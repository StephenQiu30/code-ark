# 01 Code Ark 工作箱底座与蓝图管理 PRD

唯一来源 design：[01 顶层架构与蓝图同步设计](../design/01-CodeArk工作箱顶层架构与蓝图同步设计.md)。状态：**2026-11-12审查修订已纳入合同，全部实现与运行验收未执行**。本PRD只承接此design；技术字段、目录和覆盖层规则以其为准。实施见[Plan 01](../plan/01-服务清单与蓝图同步实施计划.md)。

## 1. 摘要

用户从独立安装包获取17套蓝图和新手指南；无Git、无源码、无Node/Rust仍能物化与运行。工作箱在Docker资源层也隔离实例，复用已有服务时走显式绑定，避免以“独立目录”掩盖共用卷与旧项目名。完整处理配置插值、端口、凭据、镜像、升级及特殊路径。

## 2. 责任与确认

- 需求来源：`C01–C08`、`REQ-01/02/05/06`；审查承接 `ARK-01/02/05/06/09/11/13`。
- 维护者负责单源资产与版本锁；实现者负责无损配置和实例边界；验收人员同时检查包资源、最终模型和真实连接，不以字段存在替代有效配置。
- 用户已授权修订设计和计划，未授权本轮开发代码。本文采用的具体技术取舍归来源design，不回填成用户历史原话。

## 3. 背景与范围

原模板仍供CLI用户使用；桌面资源来自构建期提取和运行时覆盖，不修改原服务YAML/样例。MediaCrawler属于单独宿主机指南，不能以其需要Git否定17套基础设施的用户端免Git要求。Docker仍是系统前置，安装/复检由对应环境和界面PRD承接。

## 4. 目标与成功标准

1. 包含17套服务、1指南、7预设和全部辅助资产，零本机秘密/数据残留。
2. 两工作区与旧CLI实例并存时，各自资源、状态、数据和操作范围准确。
3. 任何展示/复制的连接信息与实际已应用配置一致，改端口不破坏后台连接。
4. 配置与蓝图升级保留原值和用户改动，遇不兼容/歧义给出可恢复门禁。
5. 镜像与架构支持有锁和实机证据，不把`latest`或构建通过当可复现发行。

## 5. 使用者与场景

### US-01 · 无Git用户从安装包获取完整蓝图

作为新手，希望只安装工作箱和受支持Docker，就能选择服务启动，不必克隆源码或准备SQL。

- 来源：design §7.1–7.3；`PRD01-R01/R02/R03/R06`。
- 正常：安装包自带目录和资源，首次启动在可写工作区物化，无缺文件/隐藏仓库路径依赖。
- 边界：中文/空格/非默认盘符、无Git/Node/Rust；包资源只读；缺关键资产须阻断发行。
- 异常：工作区不可写可重新选择，不能退回修改安装目录或源码目录。
- 追踪：`TS-01/TS-04`；Plan01任务1–2。

### US-02 · 保留自定义配置、端口和数据

作为日常开发者，希望修改端口或升级工具箱后，仍使用我的真实密码和原数据，手改文件不会被悄悄替换。

- 来源：design §7.3–7.6；`PRD01-R03/R04/R05/R06`。
- 正常：有效配置保留，变更预览包含实际重建范围；就绪后的连接片段来自已应用generation。
- 边界：值含`=/$/#/引号`、已有文件与公开样例同值、Kibana公开样例不符合通用占位前缀；新建实例与已初始化实例按不同策略处理。
- 异常：旧数据与凭据失配需验证/修复，不能自动生成新密码；用户手改蓝图保持原文件并等待选择。
- 追踪：`TS-02/TS-03/TS-14`；Plan01任务3–5。

### US-03 · 维护者维持单一来源及可验证发行

作为维护者，希望修改原模板后自动提取全部运行资产，并对镜像版本、架构和实例覆盖做严格校验。

- 来源：design §7.1/7.5–7.7；`PRD01-R01/R02/R05/R07`。
- 正常：构建产物可追溯源提交/校验和，不手工复制第二套配置，所有网络/卷引用可解析。
- 边界：源码`latest`必须在发行覆盖层锁定digest；不支持的CPU明确阻断该目标发行。
- 非破坏性：源码目录、已有工作区、旧容器及外部资源不因同步脚本受改动。
- 追踪：`TS-01/TS-03/TS-15`；Plan01任务1/4/6。

## 6. 价值

让模板复用、实例隔离与新手连接形成一个确定的合同。已有环境复用不要求删除旧容器；新托管实例不假装已经迁移旧数据。

### 7.4 验收测试场景

每项角色均为维护者/验收人员；静态单元场景与实际Docker/安装包场景分开登记，不能互相替代。

#### TS-01 · 全量资源与镜像锁

- 目标：R01/R02/R07；US-01/03。前置：原模板和含合成秘密/数据/软链接的隔离fixture。
- 步骤：同步→核验17/1/7、SQL/conf/脚本/补丁/指南及所有bind/build引用→扫描产物与LF→核验每目标镜像锁及插件校验和→分别检查candidate和release门禁。
- 结果：必要空目录声明明确，禁止资产为0；缺文件、越界、未解析digest或架构清单不匹配阻断candidate；实机pending允许隔离候选构建/验证，但必须阻断公开release；源目录不变。制品证据在包外关联同一SHA，不通过回写包内锁反复改变待验收制品。
- 例外：不能把未知CPU自动切模拟执行后算原生通过。
- 证据：未执行。

#### TS-02 · 无损合并与首次秘密策略

- 目标：R04；US-02。前置：含中文注释/CRLF/无末尾换行及特殊字符值的fixture，区分全新和已有实例。
- 步骤：合并缺项→生成新实例所需字段→序列化Compose输入并解析回读→验证依赖SecretRef及已有值。
- 结果：注释/用户有效值不变；Nacos≥32字节Base64、Canal24且≤32字符、SearXNG64hex、Kibana64hex；公开默认新实例替换，旧实例不自动改；无法无损表达则报错并保留原文。
- 例外：密钥文件缺失但数据库已有时进入修复，不能当新实例重新生成；v1已初始化数据库密码禁用随机生成/服务器轮换，只能认证并更新已生效连接值。
- 证据：未执行。

#### TS-03 · 最终有效配置与端口耦合

- 目标：R05；US-02/03。前置：公开样例、合成特殊秘密、不同宿主机端口；Compose 2.20/2.24.3/2.24.4及兼容更新版本的独立验证环境。
- 步骤：旧版本门禁→生成候选并`config --quiet`→在后端解析最终模型→断言实际XXL PARAMS、Seata JDBC、Kafka/Grafana/SearXNG/Kibana端口和Nacos端口组。
- 结果：旧版本被拦截，新版本能力通过；不存在遗留发布端口、二次插值或错误网络；宿主环境同名变量不能覆盖指定输入。
- 例外：静态YAML含MYSQL_HOST字段不算JDBC通过；完整连接结果另由编排/发行矩阵验证。
- 证据：未执行。

#### TS-04 · 工作区和旧CLI完整隔离

- 目标：R03/R06；US-01。前置：两个工作区及一个旧CLI实例，使用独立测试Docker目标和端口，含Nacos固定卷fixture。
- 步骤：无Git从内嵌资源物化→启动双方→检查容器/网络/卷ID及标签→停止/清理一方→重新读取另一方数据。
- 结果：项目、固定container_name、固定volume name全部隔离；旧CLI和其他工作区不受影响；中文/空格路径可用；临时目录不能被当作充分隔离条件。
- 例外：UUID截断碰撞延长并持久化，工作区ID复制歧义进入修复而非认领。
- 证据：未执行。

#### TS-14 · 升级、手改冲突与配置保存

- 目标：R03/R04/R06；US-02。前置：已有.env/测试数据、手改Compose、新旧蓝图和不兼容镜像候选。
- 步骤：刷新候选→查看差异→选择保留用户文件→切换另一工作区→尝试不兼容升级。
- 结果：手改文件不自动覆盖，秘密及数据保留；原工作区运行实例仍有记录；不兼容迁移/降级被门禁阻断；备份不作为静默覆盖授权。
- 例外：路径越界、软链接、只读及写入中断不能破坏原文件。
- 证据：未执行。

#### TS-15 · RocketMQ三方路由

- 目标：R05/R07；US-03。前置：锁定镜像，Broker启用本地Proxy、实例网络及独立端口，匹配版本的客户端。
- 步骤：创建专用测试Topic/组→宿主机5.x SDK通过Proxy发送消费→同网容器SDK发送消费→Console查询Broker/Topic→改Proxy发布端口重复。
- 结果：三方均可达；Broker广播内网别名，未广播回环地址；UI明确旧版直连限制；不增加第二套Broker。
- 例外：任一目标不通过阻断对应发行矩阵，不能改用不可达默认值掩盖失败。
- 证据：未执行。

### 7.5 假设与边界

Tauri锁定版本的存在性不等于兼容验证；镜像digest、SDK版本和OS支持在实施/发行时按真实证据填入。v1无蓝图在线热更、无自动二进制数据库迁移；签名/公证及发行门禁由界面PRD承接，不能以未知证书状态宣称开箱已验证。

候选构建只要求锁可解析/架构匹配，不要求先有最终包实测结果；公开发行另校验包外证据与候选SHA一致。跨工作区控制索引在用户级固定位置，不能因切工作区就丢失共享依赖。
