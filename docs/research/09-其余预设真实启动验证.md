# 其余预设真实启动验证

English Summary: This record covers isolated real Engine startup, protocol probes and scoped stop checks for the remaining presets. Each case has its own guarded workspace and private acceptance configuration. A failed or resource-refused case is not marked Ready.

## 范围与隔离

2026-11-13 分阶段通过真实 `Engine.start`、协议探针和 `Engine.stop` 验证 RabbitMQ、Sentinel、Monitoring、RSSHub、SearXNG、Kafka、Nacos、RocketMQ 和 Elastic。早期仅使用既有 `prepare_acceptance`、`preset_startup` 二进制验收；发现问题后，由主任务修复模板、Rust 编排/探针生命周期及本地 Java 探针并提供新二进制，本文记录修复前后实际结果。验收另编译 `.tools` 内独立诊断类/JAR用于安全分类，不混入已锁制品；最终产品 Java/锁及 Cargo 构建由主任务统一处理。没有提交或推送。

- 根配置位于忽略目录 `.tools/preset-remaining-20261113/config.json`；各服务使用独立子目录中的私有配置、workspace、control 和随机 runId，不复用默认工作区。
- 所有配置锁定同一现场 CLI、context、target 与 daemon，保留 `AcceptanceConfig.validate` 目标/路径守卫；配置权限为 `0600`，未在文档或终端输出内容。
- 最初各项映射端口限定 `28000–28999`；Nacos耦合端口修复后按主任务明确方案使用fresh工作区及 `31000–32999`（有界跨度1999）。所有入口绑定 `127.0.0.1`；同一时刻最多运行本任务的一个服务预设，下一项启动前确认本任务其他工作区没有运行容器。
- 读取根规范及相关服务 README、Compose、`.env.example` 后测试；不覆盖已有服务配置，不复用已有业务数据库，不启停无关容器、不执行 prune。
- 运行器对每项执行两轮真实启动→协议就绪→仅停止所属容器；保留工作区、运行数据与归属标记。这里的保留证据是停止后实际数据路径/文件和所属容器挂载，不能替代所有服务业务数据的写入/灾难恢复验收。

真实命令形式如下，私有配置内容不作为公开附件：

```sh
toolbox/src-tauri/target/debug/examples/prepare_acceptance .tools/preset-remaining-20261113/<service>/config.json
# 在新建私有配置中仅调整 portMin=28000、portMax=28999。
toolbox/src-tauri/target/debug/examples/preset_startup .tools/preset-remaining-20261113/<service>/config.json <service>
```

每项忽略目录中保留 `runner.log`、`evidence.json` 和操作记录；后续运行项另采集 `ps-transitions.json`，只摘取状态、退出码、OOM/健康及挂载目的地，不公开容器环境或凭据。

## Monitoring 首轮失败证据

原始操作步骤为 `preflight → images → deploy → Failed/OwnershipConflict`，未进入 readiness。运行实例的 `containers=[]`、`applied=None`，但独立工作区标签下实际已有 Grafana 和 Prometheus 两个运行容器；因此原运行器未能通过登记记录触发 Engine.stop，不能把自动清理算作通过。

只读核验确认两容器的 daemon、名称、镜像、project/workspace/instance/service/generation/blueprint 与该配置和部署意图完全一致。Grafana bind Source 与意图相等；Prometheus 两个只读 bind 的实际 Source 为 `/host_mnt` 加原宿主路径，而意图保存原路径。`bindings.rs::verify_ownership` 严格比较 bind Source 集合，因此拒绝。此处为现场可复现的路径表示差异，不改源码或放宽守卫来使测试通过。

为释放本任务占用的资源，在再次验证 daemon 和完整归属后仅对这两个实际 CID 执行 Docker stop，保留容器和命名卷。最终均 exited(0)，但产品实例仍显示 RecoveryRequired；这是验收清理动作，**不是 Engine.stop 成功**。第一轮失败保留，第二轮未执行；后续如修复重验应另记结果。

## Monitoring 修复后恢复及新代际结果

主任务明确提供包含alias修复的二进制后，使用原私有配置恢复；这次通过部署归属核验，但readiness最终返回 `ProbeEndpointUnavailable`，未进入第2轮。原Engine.stop成功，两组件均停止、数据保留。随后主任务又提供最新二进制，按已授权的 `--rebuild` 生成新代际并重建容器，首轮仍在readiness返回同错误，Engine.stop再次成功。

现场只读后台检查：Prometheus `/-/ready` 为200且文案正确，active targets中的self为up、lastError为空；Grafana宿主API为RemoteDisconnected，容器内 `127.0.0.1:3000/api/health` 也Connection refused，因此无法归因为宿主端口转发。Grafana无OOM、无重启；新代际一度约174MiB、11线程，当前start日志持续应用/API初始化，却没有HTTP Server Listen，也没有明确error/panic。初期约2.9MiB的瞬时采样不是最终常态；没有把它当确定根因。保留日志和失败，不扩大Ready条件或擅自增加期限。

原始归属FAIL、alias恢复FAIL和最新binary重建FAIL分开保留；源码修复不等同Monitoring已验收通过。

在同一容器运行原健康完整命令，随后实测2.944秒退出0；用同一 Kafka CLI 从内部29092读取元数据，4.715秒退出0且返回broker id1。随后原Compose健康通过，UI继续启动，原Engine进入真实SDK readiness并完成第1轮。初始10秒超时记录真实保留；上述证据未能证明最初超时的根因，因此不把“Java冷启动”写成确定结论，也不把曾提出的advertised listener假设作为已证实原因。

## Monitoring 512MiB修复后的完整编排验收

独立诊断在同锁定ARM镜像、全新volume上执行256/512/256MiB的A/B/A：256MiB两次120秒无HTTP，512MiB的`/api/health`约6.328秒返回database=ok；256MiB存在cgroup贴顶、大量max事件及refault但无OOM。主任务据此将Grafana预算调整为limit512MiB/reserve256MiB、整个Monitoring最低预算1GiB，并同步模板/catalog与资源准备后明确提供新binary。

随后使用fresh `monitoring-512` 私有工作区执行两轮完整Engine闭环，均为Ready→原Engine.stop。Prometheus ready和self targets up、Grafana认证的Prometheus数据源健康、通过数据源代理的真实PromQL `up{job="prometheus"}`查询均通过。最终两容器exited、归属标记及数据保留。该成功与旧256MiB三次失败分开记录，未把提高超时或首页200当作修复。

## Nacos 首轮端口守卫拒绝

实际准备的映射为 Console `28000→8080`、Main `28001→8848`、gRPC `28002→9848`、`28003→9849`、`28004→9850`。原运行器逐个连续选取宿主端口，不满足 Nacos 主端口与gRPC端口必须保持原偏移的合同，因此 Engine 在preflight返回 `InvalidCoupledPorts`，没有创建容器。这是验收端口分配方案的缺口，不能据此宣称 Nacos 服务启动失败或通过。

本次最初指定的 `28000–28999` 窗口无法容纳Main到最后gRPC的1002端口差。主任务随后修复验收runner的组分配，将测试guard的最大跨度有界调整为2048，并明确授权fresh Nacos配置 `31000–32999`。本验收执行方不改产品源码或原失败registry。新现场只读验证实际端口为Main31000、Console31001、gRPC32000/32001/32002，偏移及隔离范围均正确；后续协议结果以表中最终记录为准，最初拒绝证据保留。

## Nacos 新隔离方案认证结果

fresh耦合工作区通过preflight/deploy，readiness最终返回 `ProbeAuthenticationFailed`，原Engine.stop成功，未进入第2轮。只读比对确认候选与实际容器的密码、token及identity字段一致；密码不作输出。实际镜像的 `docker-startup.sh` 没有引用 `NACOS_AUTH_PASSWORD`，但这本身不足以证明管理员是否已初始化。

经主任务明确授权，仅对相同私有工作区、同代际、精确归属CID启动作诊断；不调用admin初始化、不改密码。使用保存凭据的login及5秒后复核均为**HTTP403、非JSON**，顶层及data层token均不存在；所以不是成功token包装在data导致的parser误判。无token的namespace/config GET均403，JSON键只有code/message/data。诊断结束后原Engine.stop退出0，数据保留。403不能单独区分用户不存在与密码不符；后续bootstrap实现与重验由主任务继续核实。

诊断脚本最初曾先解析JSON再记HTTP，可能遗漏纯文本403；该不完整记录已排除，最终结论依据修正后的明确HTTP状态。官方[鉴权插件说明](https://nacos-group.github.io/en/docs/v3.2/plugin/auth-plugin/)列出首次admin bootstrap接口，[凭据文档](https://nacos.io/en/docs/v3.2/manual/user/auth/)给出顶层accessToken登录示例；现场结果仍以本镜像实测为准。

## Nacos bootstrap接入后的真实Engine结果

主任务完成bootstrap-only实现、所有权/目标/卷守卫和已有管理员不覆盖保护，并明确提供已接入orchestrator的新binary后，使用fresh `nacos-bootstrap` 工作区和31000–32999端口范围测试。只由Engine执行初始化，没有手动调用admin。

实际operation包含 `nacos/initialize → ManagedAdministratorVerified`，随后进入原协议readiness，说明首次管理员及保存凭据校验这一步在真实新卷上已通过。最终仍在readiness返回 `DockerCommandFailed`，未进入第2轮；原Engine.stop成功，容器exited、数据及归属标记保留。因此本次不再是旧403，但也不能把bootstrap一步成功当作完整Nacos验收。它与Rocket/Canal相同的readiness Docker命令失败现场交由主任务进一步分类；是否确实来自短命Java容器及具体退出原因仍待生命周期证据，等待有证据的修复后重验。

## RocketMQ 首轮隔离边界失败

启动前实际Docker合计约7.064GiB，低于本次协调的8GiB阈值，并确认此前本任务预设均已停止。部署及归属核验后进入readiness时，按主任务提醒立即只读核查实际 PortBindings，发现 broker 的 Proxy 端口额外绑定 `127.0.0.1:18082→8081`；该入口未进入当时catalog/effective端口清单，渲染fallback越出本次 `28000–28999` 隔离范围。其他入口均为28000–28004。

保留实际端口证据后，仅终止命令行完整匹配该私有Rocket配置的验收runner，防止继续第二轮。再次核对daemon及workspace/instance/service/generation/blueprint/project/名称/镜像/限定bind来源后，仅stop本任务3个实际容器；最终均exited，容器、卷及运行数据保留。原操作为Running、实例RunningUnverified，属于中断后需恢复的现场，**不计Engine.stop或Ready通过**。待Proxy成为正式端口合同并移除fallback后，在新验收代际/隔离配置中重验；未自行修改产品源码。

## RocketMQ 正式Proxy端口的新隔离现场

主任务将8081 Proxy加入正式catalog PortMapping并移除渲染fallback后，使用新binary和fresh工作区重验，不修改旧desired/registry。启动前Docker实际合计约6.517GiB。实际运行PortBindings核验为：broker10909/10911/10912映射28000/28001/28002，Proxy8081映射28003，Console8082映射28004，NameServer9876映射28005。全部为127.0.0.1、均在28000–28999，不再隐藏发布18082；后续协议就绪结果以表中最终记录为准，不能单凭端口修复标PASS。

## RocketMQ 新隔离工作区协议失败

正式Proxy端口范围通过后，fresh组仍在readiness返回 `DockerCommandFailed`，未进入第2轮；原Engine.stop成功，三组件均停止、归属标记及数据保留。当前start日志显示NameServer boot success、broker Proxy startup successfully、Dashboard在8082启动；三者OOMKilled=false、RestartCount=0，不能用服务进程运行代替完整探针通过。

按本轮operation时间范围查询短命探针的`io.codeark.probe-owner`存在标签及oom/die事件，结果为空；同范围不加标签/动作过滤的全部container事件也为空，因此历史覆盖不足，不能据此证明探针没有OOM。锁定JRE17镜像本机inspect为linux/arm64且存在。namesrv/broker在Engine.stop之后退出137，不将它冒充为OOM证据。当前未保留实际probe stderr，尚无足够证据将失败归因探针内存、PID或服务协议；未放宽Ready或修改探针资源。

## 短命Java启动分类与挂载源对照

主任务提供含诊断生命周期的新binary后，对同配置Nacos-bootstrap、正式Proxy的Rocket工作区串行加 `--live` 重验。两者都在readiness终局返回固定分类 `ProbeClientLaunchFailed`；最后摘要均为status=Cleaned、cleanupCode=null、exitCode=null、oomKilled=null，且未观察到containerId。Nacos另核验active owner记录0、同owner容器0。两组原Engine.stop均成功，所有服务容器停止、数据保留。没有Ready，因此没有LIVE_PASS；null不是OOM=false，更不是OOM证据。

随后主任务在Canal零输入对照中确认原resource bind源对daemon不可见。本验收对Rocket的rocket-route bundle独立复核：原Mac目录存在、目录0755/JAR0644、每个文件均匹配artifacts.lock；保持锁定JRE17、256MiB/heap128MiB、pids96、uid65534、只读、network none及空输入，仅执行java-version。原resources路径退出125，Docker明确报bind source path不存在于/host_mnt映射；仅按白名单逐文件hash复制到当前私有新路径后，同一命令退出0并启动Temurin17.0.21。

这直接证明原挂载源在daemon视图不可见，未调用SDK或任何服务、未提高资源。不能据此宣称Docker Desktop的具体缓存机制已经证明。主任务据此实施严格hash白名单的immutable staging，等待新binary后才重验；不反复尝试旧binary或把失败当跳过。

## immutable staging后启动Ready与live外围失败

新staging binary使用同一Nacos-bootstrap配置重验，startup已真实Ready，完整启动协议通过；旧last-failure已移出原位置，本轮没有产生新的Java失败摘要。随后验收运行器清掉启动证据、强制后台重验的`--live`阶段返回 `DockerCommandFailed`，未出现LIVE_PASS、未进入第2轮；原Engine.stop成功。不能把startup Ready直接算完整live验收。

只读对原同CID执行live_status.rs完全相同的Go模板，Docker退出1，明确为访问 `.HostConfig.Mounts` 时map缺少Mounts键；原inspect同时缺少State.Health。该错误发生在live外围投影，未进入新Java启动失败记录，不能继续归因SDK或OOM。主任务改为safe index/with后，已对同类owned停容器验证exit0且合法JSON、缺失字段为null；不放宽归属或协议条件。待修复版binary编好后才执行最终两轮--live重验。

## Nacos最终两轮startup/live/stop验收

主任务编译safe optional live投影修复版后，同一Nacos-bootstrap私有配置执行 `nacos --live` 两轮。每轮均取得startup Ready；运行器清掉启动证据、invalidate后台缓存并强制新协议观测后取得LIVE_PASS；随后原Engine.stop成功。第二轮同样完整通过，最终容器exited，保存凭据、数据及归属标记保留。

该结果包含既有管理员凭据复用、Console namespace/config后台及真实Nacos SDK探针；首次bootstrap在此前fresh卷上由Engine完成的ManagedAdministratorVerified证据保留。旧耦合拒绝、403、Java挂载源错误及live外围投影失败均未删去或冒充通过，最终两轮的runner.log、run-metadata.json与binary-sha256.txt对应本次成功。

## RocketMQ 分协议只读debug

staging及safe optional投影修复后的Rocket仍在readiness返回 `ProtocolUnavailable`，本轮没有新的launch/process失败摘要，原Engine.stop成功。为分辨具体协议，主任务明确授权对同私有配置、同代际、完整daemon/部署意图/标签验证后的3个原CID精确启动作debug；不重复整轮聚合验收，不写消息或创建topic。

等待Console后台实际列出broker后，在各组件network namespace使用已staged且逐文件重新匹配artifacts.lock的bundle各跑一次，保留同JRE/256MiB/heap128MiB/pids96/只读权限：Console status=0且brokerAddrTable非空；rocket-route固定JSON为success=true/errorCode=null；rocket-proxy固定JSON为success=false/errorCode=ProtocolUnavailable。仅Proxy SDK失败。两个诊断客户端按独立nonce/name/task标签精确清理，最后原Engine.stop退出0，保留服务数据；debug不计Ready。

主任务从当前锁定的rocketmq-client-java5.2.2字节码确认ClientConfigurationBuilder默认sslEnabled=true，而本地Proxy为plaintext；该候选与唯一Proxy失败一致。若修复，将只让本地客户端显式使用实际传输契约，不更改服务TLS或放宽协议成功条件；仍以新binary两轮startup/live/stop实测为准。

## RocketMQ 显式plaintext客户端后的复核

主任务将本地rocket-proxy客户端显式设置enableSsl(false)，更新该模块JAR及锁定校验和后提供新binary；服务TLS、SDK成功条件、预算及权限均未改变。完整Engine首轮仍在readiness返回 `ProtocolUnavailable`，未取得Ready/LIVE_PASS，原Engine.stop成功。

使用当前新lock对应的staged模块再次按已授权的独立只读debug分辨：Console status0且broker表非空，route SDK成功，Proxy SDK仍ProtocolUnavailable；两SDK进程正常退出且无OOM，最后Engine.stop成功。故不能把SSL默认值候选直接写成已解决根因，继续要求仅Proxy的安全异常分类/响应码证据，不反复无修复运行整轮、不创建topic或发送消息。

## RocketMQ 系统Topic拒绝的确切根因

私有阶段诊断按原12秒check预算分别记录build/close，只输出安全异常类、响应码及已知模式。实际约677ms即在build失败，异常链为IllegalStateException/RuntimeException/ExecutionException/BadRequestException；SDK响应码40002（ILLEGAL_TOPIC），已知模式为SystemTopicForbidden。没有进入close，不是close耗时或整体Timeout。

该证据与[RocketMQ 5.5.0 GrpcValidator](https://github.com/apache/rocketmq/blob/rocketmq-all-5.5.0/proxy/src/main/java/org/apache/rocketmq/proxy/grpc/v2/common/GrpcValidator.java)禁止system topic的实现一致，原探针将公开系统Topic `TBW102` 当作普通Producer预声明Topic的假设不成立。改用不创建Topic、不发送消息的真实settings协商与heartbeat成功应答方案；不能仅以空topics Producer对象非null代替协议成功。最终探针实现、锁更新和binary由主任务统一完成，仍以最终两轮startup/LIVE_PASS/stop为准。

## RocketMQ最终两轮startup/live/stop验收

主任务最终让本地Proxy客户端不请求任何Topic：使用锁定5.2.2的公开ClientImpl API，必须收到真实Telemetry settings回包且Code.OK、clientType=PRODUCER、publishing存在，然后显式等待heartbeat Code.OK。完成后精确通知同一临时client session终止并关闭stream；整体仍为原12秒check预算，JRE256MiB/heap128MiB/pids96、服务TLS及其他SDK成功条件均未放宽。不以对象非null、TCP可连接或错误应答代替协议成功，不创建Topic、不发送消息。

最终binary运行前Docker实际占用约6.698GiB。使用原正式Proxy私有配置执行 `rocketmq --live` 两轮，每轮均startup Ready；清掉启动证据并强制后台重新协议确认后均LIVE_PASS；随后原Engine.stop成功。第二轮同样完整通过，最终3容器exited、messageCode=null、归属标记及数据保留。该结果同时要求NameServer真实broker路由、Proxy SDK协商和Console真实后台broker表通过；原系统Topic拒绝、挂载源不可见及live投影失败证据保留，没有被改写为成功。

本记录9项预设最终为**8项完成两轮启动/停止保留**，其中Nacos/Rocket追加两轮强制新协议观测；Elastic按现有资源真实拒绝，不能宣称完整栈Ready。消息收发、业务Topic、负载/故障及跨平台安装仍不在上述协议/后台连接验收范围内。

## Elastic 完整栈资源预检

其他本任务预设停止后，按Engine同一公式核算daemon总内存减实际运行占用及512MiB预留，现场可用约4.633GiB，小于完整Elastic最低6GiB。真实Engine.start在preflight返回 `InsufficientMemory`，没有创建任何Elastic容器；第二轮不适用，没有停止其他项目来腾内存。不将这个结果写成Elastic完整栈Ready；ES/IK单镜像在独立低内存配置下的既有验收也不替代完整栈验收。

## 限制与失败处理

任何失败首先保留操作步骤和错误码，检查所属容器状态、退出码、OOM/健康和已脱敏必要错误摘要；不修改 Ready 规则、权限或源码来绕过失败。资源拒绝、外部搜索引擎不可达、后台连接失败分别记录，不用首页 HTTP 200 代替协议探针。

本记录只覆盖表中实际执行范围。AMD64、其他桌面系统、签名安装包及完整故障矩阵仍需独立验证；ARM64 镜像制品独立功能与下载证据见 [制品验收](07-ARM64预构建镜像制品验收与发布.md)，桌面全局消息及依赖预设结果见 [桌面与预设验证](08-桌面全局消息与预设启动验证.md)。
